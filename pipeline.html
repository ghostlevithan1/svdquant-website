Pipeline deep-dive

From a dense model to a 4 to 6 bit file

svdquant works in two halves. Compression measures the model once and chooses a precision for every layer. Runtime then reads the packed factors directly, so the full weight matrix is never rebuilt when a token is decoded.

Calibrate→Sweep candidates→Allocate bits→Factor and quantize→Store→Decode
1

Calibration: measure what matters

The model runs over a small calibration text once. For each linear layer, the pass records the uncentered activation second moment C = (1/N) X Xᵀ. This matrix says which input directions the layer actually uses, so errors in those directions count more.

The same C drives three later decisions: the scale search, the error metric, and the bit allocation. No extra pass is needed. Large matrices are whitened with a Cholesky factor when an eigendecomposition would be too slow.

Where: svdquant/hf/calibration_cache.py, svdquant/svd/
2

Candidate sweep: try many ways to store each layer

Each layer is tried under a grid of options: factor rank, bit width (4, 6 or 8), group size (16 to 256), and asymmetric or symmetric codes. Every candidate is scored by its real stored size, counting codes, scales, zero points, padding and layer headers, and by its measured error. Candidates that are strictly worse on both size and error are dropped, which is exact because they can never be chosen.

  • Coarse-to-fine rank search: a coarse ladder first, then a full search near the best rank.
  • Search modes: fast, balanced (default), and thorough.
Where: svdquant/allocator/candidates.py, svdquant/allocator/sweep.py
3

Allocation: spend the bit budget where it helps

Layers are not compared by their relative error. They are compared by the absolute error energy tr(ΔW C ΔWᵀ), which is the damage a layer does to the network's output. A global budget then assigns each layer a candidate so that total damage falls fastest per byte. Sensitive layers keep their precision, and tolerant layers give some up.

Some layers are protected: their caps are relaxed and they stay at 8 bits when the budget allows. That protection is why the best measured point (5.77 bits per weight) reaches 13.3 perplexity.

Where: svdquant/allocator/budget.py
4

Factorization and error compensation

Each weight matrix is split into two low-rank factors, A and B, using a truncated SVD (or a randomized range finder with a seeded projection, so builds are reproducible). Each factor is quantized on its own, and the rank is validated by its residual.

For int4 layers, GPTQ-style error compensation updates the remaining columns after each rounding step, using a Cholesky factor of the inverse Hessian built from C. The update divides by the Cholesky diagonal, which is the square root of each pivot, not 1. A safety net compares the result against the plain searched quantizer and keeps the plain result unless compensation wins by at least 2%.

Where: svdquant/svd/decompose.py, svdquant/quantizers/optimized.py
5

Scale search: clipping instead of min and max

Each group's scale and zero point are searched over clipping ratios, weighted by the importance from C. A few local refinement passes polish the result, with no host synchronization. The plain min and max rounding option was removed from the pipeline: it saved little VRAM and cost a large jump in perplexity.

Where: svdquant/quantizers/optimized.py
6

Storage: smaller on disk, still fast to load

Quantized codes are canonical-Huffman coded per tensor, and only when that saves bytes. On Qwen2.5-0.5B this saves 38.5 MiB across 246 tensors with no quality change. Scales are stored as 8-bit log-domain codes, so metadata is 0.72% of the file. The embedding table is stored as packed 8-bit codes with one scale per row, and the tied LM head shares that storage.

The file is checked by the SHA-256 of its weights. svdquant verify compares the predicted size with the real serialized size, and the container overhead measured for Qwen2.5-0.5B was 0.09%.

Where: svdquant/entropy.py, svdquant/native/entropy_codec.cpp, svdquant/hf/entropy_io.py, svdquant/nn/quantized_table.py

Runtime: how a token is produced

Decoding and prompt processing want different things, so they use different kernels.

7

Decode: fused dequantize and multiply

For one token, the Triton kernel reads the packed factors and dequantizes them inside the matrix multiply. The full weight is never written out, so VRAM stays low. Computing Y = A (B X) on the factors keeps the arithmetic small.

Where: svdquant/kernels/triton_kernels.py, svdquant/nn/quantized_linear.py
8

Prefill: dequantize once, then cuBLAS

The fused kernel repeats dequantization for every block of tokens, which is far too slow on long prompts. Above 96 activation rows the weight is dequantized once and passed to cuBLAS. On a 2,048-token forward this cut the time from 5,545 ms to 237 ms.

Where: svdquant/kernels/dispatch.py
9

CUDA-graph decode

The single-token step is captured once and replayed. A 0.5B decode step becomes one launch instead of about 340. Output is token-for-token identical to eager decoding. Sampling and CPU models take the normal path.

Where: svdquant/graph_decode.py
10

Quantized KV cache (optional)

Attention states can be stored as fp8-e4m3 codes, or int8 where fp8 is not available, with one fp16 scale per token vector. That roughly halves KV storage. It is turned on per run.

Where: svdquant/kv_cache.py
What this page does not claim. Compression is slower than the earlier baseline, mostly in the sweep. Older RTX cards are not yet tested. Sub-4-bit quality is still a goal. See the roadmap for the open items.
